# معماری و ساختار مخزن

## تصمیم و گزینه‌های ارزیابی‌شده

استفاده از Next.js به‌تنهایی ساده‌تر بود، اما درخواست استفاده از هر دو چارچوب صریح است. تقسیم پیشنهادی مسئولیت روشن دارد: Astro برای خروجی کم‌جاوااسکریپتِ خواندن؛ Next.js برای جریان‌های تعاملی حساب و تحریریه. Astro از جزیره‌های React پشتیبانی می‌کند، بنابراین ابزار خواندن قابل اشتراک است. [مستندات Astro](https://docs.astro.build/en/guides/framework-components/)

Astro کاملاً استاتیک برای این پروژه انتخاب اولیه نیست: انتشار و به‌ویژه لغو انتشار باید فوری باشد و صفحه‌های مجموعه، جست‌وجو و نقشه سایت نیز هم‌زمان تغییر کنند. SSR با آداپتور Node انتخاب نسخه اول است؛ صفحه‌های ثابت مانند درباره می‌توانند prerender شوند. [رندر درخواستی Astro](https://docs.astro.build/en/guides/on-demand-rendering/)

پیشنهاد خدمات: Supabase برای PostgreSQL، Auth و Storage؛ Next.js تنها لایه API تعاملی. PostgreSQL با SQL migrations و انواع تولیدشده استفاده می‌شود؛ ORM، Redis، موتور جست‌وجوی مستقل، صف خارجی و سامانه هویت دوم فعلاً لازم نیستند. Zod برای اعتبارسنجی ورودی، React برای اجزای تعاملی، CSS variables و CSS modules برای طراحی، Vitest و Playwright برای آزمون.

CMS جدا مانند Payload یا یک CMS میزبانی‌شده فرم‌های عمومی را سریع‌تر فراهم می‌کند، اما در این پروژه حفظ متن اصلی، تشخیص تکرار و حل شماره قسمت بخش مهمی از مدیریت‌اند و همچنان سفارشی می‌مانند. افزودن CMS می‌تواند مدل مجوز و کاربران دیگری وارد کند. در نسخه اول، یک مدیریت محدود در Next.js با همان Auth و DB ساخته می‌شود. هزینه واقعی آن شامل فرم، نسخه‌بندی، پیش‌نمایش و مدیریت رسانه است و در زمان‌بندی لحاظ شده؛ انتخاب CMS در صورت رشد تیم تحریریه دوباره بررسی خواهد شد.

## نمودار ساده

```text
Browser
   |
HTTPS gateway — یک دامنه
   |-- /app, /app/* ---> Next.js
   |                       |-- Supabase Auth: هویت و نشست
   |                       |-- PostgreSQL: RPC + RLS با هویت کاربر
   |                       `-- Storage: بارگذاری مجاز
   |
   `-- سایر مسیرها ----> Astro SSR
                           `-- PostgreSQL: فقط نسخه عمومی، نقش anon

React islands در صفحات Astro ---> /app/api/* در همان origin
تصاویر منتشرشده ----------------> Storage/CDN
```

این نمودار قراردادی است؛ هنوز هیچ زیرساختی ایجاد نشده است.

## مسیرها و نشست

دامنه واحد انتخاب می‌شود. gateway همه `/app` و `/app/*` را بدون حذف پیشوند به Next.js می‌فرستد؛ Next با `basePath: '/app'` ساخته می‌شود و assets آن زیر همان پیشوند قرار می‌گیرند. بقیه مسیرها متعلق به Astro هستند. `basePath` در زمان build تعیین می‌شود و باید در staging و production سازگار باشد. [مستندات Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/basePath)

مرجع کاربران فقط `auth.users` است. Next مسئول ثبت‌نام، تأیید، ورود، refresh، خروج و بازیابی است. مرورگر Astro وضعیت حساب را از `/app/api/session` می‌خواند؛ خود Astro نه نشست می‌سازد و نه token را refresh می‌کند. انتقال بین دو برنامه با لینک معمولی و بارگذاری کامل انجام می‌شود.

از `@supabase/ssr` در سمت سرور Next استفاده می‌شود؛ همه عملیات احراز هویت از BFF می‌گذرند و Supabase client مرورگری برای Auth وجود ندارد. cookieها host-only، با `Path=/`، `Secure` در HTTPS، `SameSite=Lax` و در این طراحی server-only با `HttpOnly` هستند. callback و refresh باید چند cookie و headerهای `Set-Cookie` را بدون حذف حفظ کنند. جریان واقعی این انتخاب در برش نخست آزمایش می‌شود؛ حالت توسعه HTTP تنها استثنای `Secure` است. اعتبارسنجی امضای token با API تأییدشده انجام می‌شود، نه اعتماد به داده خام نشست. [راهنمای SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&queryGroups=framework)

در عملیات حساس، فعال‌بودن کاربر و نقش جاری از داده مورد اعتماد سرور بررسی می‌شود؛ نقش داخل metadata قابل ویرایش کاربر معتبر نیست. برای تغییر گذرواژه، نقش یا تعلیق حساب، نشست و وضعیت زنده دوباره بررسی می‌شوند. refresh فقط در Next و پاسخ‌های بدون کش انجام می‌شود؛ redirect مقصد فقط مسیر داخلی allowlist است. [نکات نشست Supabase](https://supabase.com/docs/guides/auth/server-side/advanced-guide)

## مرزهای داده و انتشار

Astro با کلید عمومی و نقش ناشناس فقط projection عمومی را می‌خواند؛ cookie کاربر را به DB منتقل نمی‌کند. Next درخواست کاربر را با JWT همان کاربر اجرا می‌کند تا RLS باقی بماند. secret مدیریتی فقط برای bootstrap و API مدیریت Auth در ماژول جدا و auditشده است؛ عملیات معمول محتوا و مطالعه با service role اجرا نمی‌شوند.

تراکنش انتشار، نسخه تأییدشده را به `published_posts` کپی، taxonomy و ترتیب عمومی را به‌روز و رویداد audit را ثبت می‌کند. پیش‌نویس هیچ‌وقت بخشی از پاسخ عمومی نیست. ویرایش مطلب منتشرشده نسخه کار جدید می‌سازد و نسخه عمومی قبلی تا انتشار بعدی باقی می‌ماند.

در نسخه اول تمام HTML محتوایی، queryهای عمومی، sitemap و پاسخ‌های شخصی بدون کش ماندگار هستند؛ Next نیز برای queryهای حساس صریحاً `no-store` دارد. انتشار با درخواست تازه دیده می‌شود و لغو انتشار در درخواست تازه 404 می‌دهد. صفحه‌ای که قبلاً روی دستگاه باز شده قابل پس‌گرفتن نیست. مرورگر فایل‌های JS/CSS هش‌دار و تصاویر نسخه‌دار را کش می‌کند. rebuild صرفاً برای تغییر کد است.

این تصمیم هزینه SSR و وابستگی به DB دارد، اما پیچیدگی invalidation را حذف می‌کند. اگر اندازه‌گیری نیاز به HTML cache را ثابت کرد، تغییر معماری جدا لازم است: outbox تراکنشی، purge تمام وابستگی‌ها، retry و وضعیت «در حال انتشار»، و bypass امن در لغو انتشار. cache بدون این قرارداد فعال نمی‌شود.

جست‌وجو از همان PostgreSQL و فقط `published_posts` انجام می‌شود. فیلد مشتق‌شده با تبدیل ی/ي، ک/ك، ارقام و یکسان‌سازی فاصله/نیم‌فاصله ساخته می‌شود؛ نسخه دومِ بدون فاصله برای بعضی ترکیب‌ها قابل ارزیابی است. query همان تبدیل را می‌گیرد. عنوان وزن بیشتر، سپس نام مجموعه/موضوع و متن؛ بدون ادعای ریشه‌یابی فارسی. شروع با تطبیق توکن و `pg_trgm`، پارامترهای bound، محدودیت طول query و صفحه‌بندی؛ query کوتاه مسیر prefix محدود دارد. [امکانات pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)

تصاویر در Storage، با کلید نسخه‌دار و فایل WebP/AVIF مشتق‌شده قرار می‌گیرند. اصل بارگذاری و تصاویر draft خصوصی‌اند؛ نسخه عمومی تنها پس از تأیید منتشر می‌شود. محدودیت حجم پیشنهادی ۵MB، بررسی MIME واقعی، حذف EXIF، عدم پذیرش SVG دلخواه، ابعاد رزروشده و alt اجباری مگر تصویر تزئینی. هیچ تصویر مفقودی از JSON فرض یا دانلود نمی‌شود.

## ساختار پیشنهادی

```text
/
├── apps/
│   ├── reader/                 # Astro؛ صفحات عمومی و layoutهای مطالعه
│   │   └── src/{pages,layouts,components,islands}/
│   └── console/                # Next.js App Router؛ basePath=/app
│       └── src/{app,features,server}/
├── packages/
│   ├── contracts/              # Zod، DTO، enum؛ بدون secret یا DB client
│   ├── design/                 # tokenها، فونت، CSS و assetهای دارای مجوز
│   ├── ui/                     # React ساده؛ بدون next/* یا وابستگی سرور
│   ├── content/                # مدل بلوک امن، شماره‌خوان، normalization
│   ├── data-public/            # query محدود نسخه منتشرشده، server-only
│   └── data-private/           # query/RPC با هویت کاربر؛ فقط Next server
├── tools/import/               # CLI آینده و adapterهای دو schema
├── supabase/
│   ├── migrations/             # schema، grants، RLS، RPC، indexها
│   ├── tests/                  # آزمون واقعی مجوزهای DB
│   └── seed.sql                # داده نمایشی ساختگی و مجاز
├── tests/{e2e,fixtures}/        # مسیرهای بین برنامه‌ها و fixture حداقلی
├── infra/                      # gateway و دستور استقرار
├── docs/                       # طرح، ADRها و runbookهای آینده
├── .env.example                # فقط نام متغیرها و مقدار نمایشی
├── package.json
├── pnpm-workspace.yaml
└── pnpm-lock.yaml
```

در حال حاضر فقط `docs/` ایجاد می‌شود. pnpm workspace کافی است؛ Turborepo در این اندازه توجیه ندارد. نسخه‌های پشتیبانی‌شده Astro، Next، Node، pnpm و React مشترک در فاز نخست از نظر سازگاری بررسی و دقیقاً در lockfile و راهنمای setup ثبت می‌شوند.

اجزای اشتراکی شامل دکمه، ورودی، کارت مجموعه و رندر امن بلوک‌ها هستند؛ route، auth و layoutهای وابسته به چارچوب اشتراکی نمی‌شوند. Astro فقط جزیره‌های لازم را hydrate می‌کند. import از `data-private` در browser یا Astro با lint و export boundary ممنوع است. DTOهای API مستقل از سطر کامل DB هستند و هیچ متن اصلی یا اطلاعات حسابی تصادفاً به public bundle وارد نمی‌شود.

هزینه داشتن دو برنامه: دو build، دو runtime، هماهنگی نسخه React، asset routing، عبور cookie، ناوبری کامل بین برنامه‌ها و آزمون انتشار هماهنگ. یک origin، یک DB، یک Auth، قراردادهای مشترک و برش end-to-end اولیه این هزینه را محدود می‌کنند. این پیچیدگی با انتخاب چارچوب از بین نمی‌رود و باید در استقرار آزمایش شود.
